# SWIM's PLA and Thallium baselines, re-run locally

SWIM ships one result each for PLA and Thallium (`SWIM/tools/THALLIUM/{pladapt,
thallium}-0.{sca,vec}`, seed-set 0) and only a *mock* of the PLA library
(`SWIM/src/model/pladaptMock/`), so neither had been re-run. This directory finds
the code that produced those files, rebuilds it in Docker on this machine,
checks the rebuild against the shipped result, and runs it over seed-sets 1-10.

**Outcome.**

- **PLA** is rebuilt from published code and reproduces the shipped run
  decision for decision (utility 4089.0882 against 4089.0898). Over seed-sets
  1-10 it scores **4089.09 ± 0.00**.
- **Thallium** runs the same manager with a trimmed relation, and the trimmed
  relation the shipped run used was never published. The released Thallium
  pipeline reproduces the paper's static trimming experiment exactly, but none
  of its documented settings reproduces the shipped run. A parameter search
  found one setting that does, decision for decision (4658.6520 against
  4658.6520). That relation is **reconstructed by search, not recovered**; see
  "Thallium" for how much the match pins down. Over seed-sets 1-10 it scores
  **4658.65 ± 0.00**. Unlike the relation, this number does not depend on the
  reconstruction.
- **PLA re-targeted to SEAMS 2017A** (patch `swim-02`, section "PLA
  re-targeted to SEAMS 2017A"). This is the same planner with our utility as
  its objective. The result depends almost entirely on one input that
  Stevens's port does not give in SWIM's units: the M/M/c service time. On
  ClarkNet, seed-sets 0-9:
  - **−15,130 ± 1,016** with the configured mean, 0.030 s (the primary
    variant, declared before any result);
  - **11,263 ± 0** with SWIM's documented typical service time, 1/maxServiceRate;
  - 5,283 ± 0 with Stevens's own inputs.
  None reaches the best fixed configuration, 12,891.6.
- **WorldCup vs ClarkNet** (patch `swim-03`, section "Does adaptation pay on
  WorldCup?"): a fixed-configuration grid against the adaptive managers on
  both traces.

## What was changed, and why

Nothing in `SWIM/` (the tracked tree), and nothing in the manager's logic. The
image `selas-swim-pla:dev` (`Dockerfile`) is built `FROM gabrielmoreno/swim:latest`,
the image every other SWIM run of ours uses (OMNeT++ 5.4.1, gcc 5.4, Boost 1.58,
its compiled queueinglib), and adds:

1. clayness/swim @ `cfad67a`, built in the container. Clay's `src/Makefile` was
   generated for OMNeT++ 5.2.1, so it is regenerated with `opp_makemake` using
   his flags plus his hand-added `-lyaml-cpp`.
2. `patches/swim-01-omnetpp-5.4.1-cacheRequestCount.patch`: the one source change
   SWIM itself needed for OMNeT++ 5.4.1 (cps-sei/swim `44289ef`, verbatim).
   `MTBrownoutServer::cacheRequestCount` becomes `int` (5.4.1 refuses to read an
   int parameter into a double) and `-1/x` becomes `-1.0/x`. The value is the
   same. Without it every run stops at network initialisation.
3. queueinglib is **copied** next to the checkout, not symlinked. OMNeT++
   resolves NED paths through the link, misses queueinglib's `package.ned`
   namespace, and fails with "Class Sink not found".
4. yaml-cpp 0.5.2 from xenial (`libyaml-cpp-dev=0.5.2-4ubuntu1~16.04.4`), and
   openjdk-8 to compile `reach` and Thallium's Java.
5. The PLA relation, generated at build time by `make_reach.sh` into
   `/headless/pla/yaml/pladapt/`. It does what thallium's `run_reach.sh rubis`
   does. Alloy's enumeration is deterministic here: a host-side run produced
   byte-identical files.
6. For Thallium: PRISM-games 2.0.beta3 and the jars from thallium's
   `build.gradle`, with its Java compiled in place.
7. `patches/swim-02-seams2017a-planning-utility.patch` adds a NED parameter
   `planningUtility` to `ProactiveAdaptationManager`. Its default, `"stevens"`,
   leaves the shipped behaviour untouched; this was re-checked after the
   patch, decision for decision against the shipped run, at 4089.0883. The
   other values select the new class `Seams2017aPlanningUtility` (described in
   "PLA re-targeted to SEAMS 2017A").
8. `patches/swim-03-static-manager.patch` adds `StaticAdaptationManager`. At
   t = 0 it sets `servers` and `dimmer` and then holds them. Servers are added
   and removed one at a time (the next add waits until no server is booting,
   tested as `getServers() > getActiveServers()` as SWIM's Reactive manager
   does), because SWIM does not support concurrent boots or removals; from 3
   servers a target of n > 4 is reached after n − 3 boots. With no targets it
   does nothing. Checks: doing nothing scores 5101.2 on ClarkNet (the anchor is
   5101), and 4 servers at dimmer 1.0 scores 12,891.6 (the anchor is 12,891.6);
   12 servers on WorldCup adds at t = 0, 180, ..., 1440 s.

   *Fixed 2026-10-08.* The first version added servers in a `while` loop at
   t = 0. For targets of 5 or more SWIM refused the second concurrent add, the
   loop spun forever, and each such run grew to ~5 GB until the laptop ran out
   of memory. `run_sa.sh` now also caps every container (`PLA_MEM`, default
   2 GB) and every run's wall time (`PLA_TIMEOUT`, default 900 s), and the grid
   was re-run in full on the fixed image.

For these patches the runs use `swim_sa_planners.ini` rather than Clay's ini,
via `run_sa.sh`. It is Clay's ini with both traces and all boot delays in
SWIM's own run numbering (3 = WorldCup at 180 s, 8 = ClarkNet at 180 s), a
configuration for every manager, and no per-server vectors, which the scorer
does not read.

The manager reads `/headless/yaml/rubis{,-step}.yaml`, a hard-coded path. Each
run mounts its relation there read-only and keeps a copy in its output
directory.

# PLA re-targeted, reactive managers, doing nothing -- both traces, seed-sets 0-9 (~3 min):

## Validation: PLA, seed-set 0

| | re-run | shipped |
|---|---|---|
| utility, SEAMS 2017A (`swim_utility.py`, as `collect.py`) | **4089.0882** | **4089.0898** |
| `utility:last` (SWIM's ICAC 2016 scalar) | 4067 | 4067 |
| late periods (of 90) | 0 | 0 |
| mean servers / mean dimmer | 2.8000 / 0.1753 | 2.8000 / 0.1753 |
| `transitionsEvaluated`, 91 decisions | identical, decision by decision | |
| server-count and dimmer changes | 37 / 37 / 6, same values in the same order | |
| largest time offset of a change | 0.072 s | |
| mean decision time | 39 ms | 63 ms |

The decisions are the same, and so is the relation: `transitionsEvaluated`
depends only on the relation and the configuration at each decision, and all
91 values match. The 0.0016 left in the utility comes from timing. SWIM applies
a tactic after the **wall-clock** time the decision took (`simulateDecisionDelay`,
default true; 63 ms on Clay's 2019 laptop, 39 ms here). So each change lands up
to 0.07 s earlier, which shifts the time-weighted averages and the requests
that see the change.

**Determinism.** Because of that delay, tactic times depend on machine speed by
milliseconds. At 39 ms and at 63 ms per decision the decisions were the same.
Turning the delay off does **not** give a machine-independent equivalent.
`SELAS_PLA_DECISION_DELAY=false run_planners.sh ...` applies each tactic at the
timestamp of the period event, via a copy of the ini mounted over the original.
That changes the order of events at that instant, and with it the decisions:
58 of 91 counts differ, and utility is 4099.29 for every seed-set 0-10
(`results-local/swim_planners/pladapt-nodelay-20261008-004410/`). Use the
default (`true`), as the shipped runs did; the knob is kept only to show this.

## Results: PLA, seed-sets 1-10

Configuration: ClarkNet, boot delay 180 s, servers from 3 up to 12, 10 dimmer
levels, 60 s period, 6300 s, first 900 s unscored (90 scored periods). This is
the configuration in clayness/swim's `swim_sa.ini` (`pladapt`, run 0) and the
same as SWIM's run 8 that our other baselines use. Scorer: `collect.py` /
`swim_utility.py` (SEAMS 2017A).

| planner | seed-sets | utility (mean ± SD) | late periods | mean servers | mean dimmer |
|---|---|---|---|---|---|
| PLA (PLA-SDP, Stevens's SWIM port) | 1-10 | **4089.09 ± 0.00** | 0 ± 0 | 2.80 ± 0.00 | 0.175 ± 0.000 |
| PLA | 0 | 4089.09 (shipped 4089.09) | 0 | 2.80 | 0.175 |
| Thallium (same manager, reconstructed trimmed relation) | 1-10 | **4658.65 ± 0.00** | 0 ± 0 | 2.00 ± 0.00 | 0.456 ± 0.000 |
| Thallium | 0 | 4658.65 (shipped 4658.65) | 0 | 2.00 | 0.456 |

For reference (RESULTS.md, same scorer): doing nothing scores 5101, and SWIM
Reactive scores −2619 ± 974 over seed-sets 1-10. "Dimmer" is the scorer's
`1 − brownoutFactor`. With 10 levels and `dimmerMargin` 0.1, the manager's
steps from the initial 0.9 land on 0.9 − k/9.

Output: `results-local/swim_planners/pladapt-20261008-001531/` and
`results-local/swim_planners/thallium-20261008-035351/`. Each holds
`summary.txt`, `results.json`, and one directory per run with the `.sca`, the
`.vec`, the relation used and SWIM's log.

**Why the spread is zero.** The planner's inputs are the arrival rate
(deterministic: it comes from the trace) and the configuration. It never reads
response time. So every seed-set makes the same 91 decisions, checked with
`compare_shipped.py` on seed-sets 1, 5 and 10. Only response times vary with
the seed, and the worst per-period mean is 0.024 s against the 0.75 s threshold.
With no late period and the dimmer never at 1, so no server-cost credit, SEAMS
2017A reduces to revenue, arrivals × (1 + 0.5 × dimmer). That is the same in
every run, to the fifth decimal. A ten-seed SD for this planner is therefore
**not** evidence of robustness to SWIM's randomness: on this trace the
randomness never reaches its decisions.

## Thallium

### What the shipped run records

From the first scored decision (900 s) to the end, the shipped Thallium run
stays in configuration (1, 4, 2): 2 servers, dimmer level 4 (factor 0.456),
no server booting. All 91 decisions record `transitionsEvaluated` = 48,108.
That count is a pure function of the relation and the current configuration
(`reach_stats.py`):

    3·|RI(c)| + 9·Σ_{s∈RI(c)} |RFC(s)| + 72·Σ_s |RFC(s)|

48,108 ≡ 3 (mod 9), so 3·|RI(c)| ≡ 3 (mod 9), and |RI(c)| ∈ {1, 4} at
(1, 4, 2). A run that never moves fits
|RI(c)| = 1: the no-op is the only transition left, (1, 4, 2) is a sink, and
Σ|RFC| = 668 (PLA's untrimmed relation has 1,382). The configurations before
900 s are not recorded. To be at (1, 4, 2) by then, starting from (2, 8, 2)
(3 servers, dimmer 0.9), the six decisions at 540-840 s must include one
server removal and four dimmer decrements.

### 1. The released pipeline at its documented settings does not reproduce the run

`thallium_pipeline.sh` runs clayness/thallium's pipeline as released. Its two
call bugs are worked around without editing the scripts (see the script's
header). With `default.env` and the 16 weightings of `default.weights`, it
keeps 416-532 of the 1,172 transitions. That is 640-756 trimmed, mean 63.2%:
**exactly the paper's Experiment 1**, so the pipeline is the paper's. But at
(1, 4, 2) these relations imply 30,837-42,531 transitions evaluated, not 48,108.
Simulated on seed-set 0, three of them score −22,489, −24,238 and +5,502
against the shipped 4,659. The trimmed relation decides everything.

Variants run through the real pipeline (PRISM-games):

| variant (16 weightings each) | counts at (1,4,2) | nearest to 48,108 |
|---|---|---|
| THRESHOLD 750 ms (SWIM's SLA) | 45,156 to 61,395 | 47,940 (the code's default weighting, 0.25/0.50/0.25) |
| THRESHOLD 750, max arrivals 130 | 45,012 to 61,251 | 47,580 |
| THRESHOLD 750, 60 s steps | 38,028 to 57,936 | 48,351 |

None hit 48,108. Changing the Pareto step itself didn't either, tried on the
`default.env` bounds only: single objectives, pairs of objectives, and
comparing the pessimistic, likely or optimistic value instead of the weighted
minimum. That exploratory script is not kept.

### 2. Search

`thallium_search.py` re-implements the pipeline in Python (bounds as a
dynamic programme with PRISM's semantics, fuzzy values, Pareto trim). It is
verified against four real pipeline runs: all 1,080 bound values equal PRISM's,
and the kept counts equal the Java trimmer's for every weighting. It takes
under a second per setting instead of six minutes.

- **Documented values only.** The grid takes each constant from a value that
  appears in Clay's files (`default.env`, `run_rubis.sh` defaults, the model's
  comments) or in SWIM (750 ms SLA, 60 s period). The values are DIMMER_ADJ
  {1.15, 1.5, 2.0}, THRESHOLD {750, 3000, 4000}, server cost {0.10, 0.07},
  expected arrivals {42, 0}, max arrivals {200, 20, 130} and step {10, 60} s:
  216 settings × 16 weightings. One relation gives 48,108; two settings
  produce it, differing only in server cost (THRESHOLD 4000, 60 s steps,
  weighting 0/0/0.99, the rest `default.env`). Simulated, it is at 1 server at
  900 s, changes servers 12 times and scores 4032. **A matching count alone is
  coincidence-prone.**
- **Wide grid.** THRESHOLD 250-5000 in steps of 250; DIMMER_ADJ
  {1.1, 1.15, 1.2, 1.25, 1.3, 1.5, 2.0}; expected arrivals {20, 30, 42, 50,
  60}; max arrivals {100, 130, 150, 200}; step {10, 60} s. That is 5,600
  settings × 16 weightings = **89,600 relations**
  (`results-local/swim_planners/thallium-search/sweep.txt`). **21** give
  48,108 at (1, 4, 2). Two filters follow from the shipped run: (1, 4, 2) must
  be a sink, and it must be reachable from (2, 8, 2) within 6 decisions.
  **One** relation passes both, reaching the sink in 5 decisions, the minimum
  of one removal and four dimmer steps: THRESHOLD 1250, DIMMER_ADJ 1.25,
  expected arrivals 30, max arrivals 130, 60 s steps, weighting
  (0.00, 0.50, 0.50).
  The rest is `default.env`: horizon 10, service rate 10, server cost 0.10/h.
- That relation was then **regenerated with the real pipeline** (PRISM-games,
  the Java trimmer, `thallium_trim.py`), and the two are transition for
  transition identical: 618 of 1,172 kept, 47.3% trimmed. It is at
  `results-local/swim_planners/thallium-reconstructed/trim0.00-0.50-0.50/`
  (`rubis.yaml` md5 `21c702db45dcefc87400366946f3fcf9`).

### How strongly this pins the relation down

**It is a reconstruction found by search, not the published or recovered
relation.**

What the match shows:

- With the released pipeline, some setting yields a relation consistent with
  every number the shipped run records.
- The documented settings (the ones that reproduce Experiment 1) do not, so
  Experiments 1 and 2 cannot both have used `default.env` with the released
  code.

What it does not show:

- The run constrains the relation only through one integer (the count at one
  configuration), the sink, and a path through the unrecorded warm-up.
  Everything else about its 618 transitions is unconstrained by the data. Any
  relation meeting those three conditions would write the same files.
- One plausible hit among 89,600 measures how rare a match is in this grid. It
  is not a probability that this is the relation that was used. The trimmer of
  January 2019 predates the July 2020 release, and a different code version or
  setting could meet the same constraints.
- Two of the constants are plausible: max arrivals 130 is the paper's "0 to
  130 requests per period", and 60 s is SWIM's period. Three appear nowhere:
  1250, 1.25 and 30.

Report it as "Thallium, relation reconstructed to reproduce SWIM's shipped
run", not as Thallium per se.

### What the ten-seed number depends on

It does **not** depend on the reconstruction. The manager's inputs are the
trace's arrival rate and the configuration, and neither depends on the seed.
So with the relation that was actually used, every seed-set makes the same
decisions before 900 s as the shipped run. It is therefore in the (1, 4, 2)
sink at 900 s and stays there. The same holds for ours. (This rests on the
manager build, which PLA validates, and on decision times of milliseconds not
changing decisions, also seen with PLA.)

Seed-sets 1-10 then run the shipped configuration (2 servers, dimmer 0.456)
for all 90 scored periods. The seed moves only response times, which peak at
0.133 s, so every seed-set scores 4658.651979641203 to the last digit printed.
**On this trace Thallium does not adapt after the warm-up: it is a static
configuration**, and it scores below doing nothing (3 servers, dimmer 0.9: 5101).

## PLA re-targeted to SEAMS 2017A

The shipped planners plan for Stevens's utility, not ours, so they are an unfair
baseline. Patch `swim-02` gives the same planner our objective.

### What changes, and what doesn't

Only the per-period utility that PLA-SDP maximises over its 10-period
look-ahead changes. Everything else stays as in Stevens's port:

- the reachability relation (the full PLA one, 340 configurations);
- the LES predictor and its scenario tree;
- the tactics and the 60 s period;
- the manager code that maps SWIM's state to a configuration.

The new `Seams2017aPlanningUtility` is `periodUtilitySEAMS2017A` from SWIM's
`plotResults.R`, written as `swim_utility.py` computes it. For a planner
configuration (s, d, p) and the predicted arrival rate λ (req/s, the value the
manager already predicts):

    dimmer       df = d/9
    servers      active = s + 1 (the manager encodes active − 1);
                 provisioned = active + 1 while a server boots (p not idle)
    revenue      ur = λ·((1 − df)·1 + df·1.5)
    not late, ur ≥ 1.5λ − 1e-5 (dimmer 1):  ur + 10·(12 − provisioned)
    not late, otherwise:                     ur
    late (predicted rt > 0.75 s):            min(0, λ − 12·maxServiceRate)·1.5

"Provisioned" is what the scorer averages (`serverCost`). Stevens's own
expression, `s + (p > 0 ? 1 : 0)`, mixes up the 0-based server count with the
progress encoding (p = 2 means idle); it belongs to the utility being replaced.

### The predicted response time

Stevens's M/M/c call is

    MMcQueue::totalTime(s, 0.001·1.2^(9−d), 60000/λ, …)

compared with 3000 ms. That is c = active − 1 servers, arrival rate λ/60 per
second, and service rate 1.2^(9−d) per second. These are not SWIM's units: at
full dimmer the service alone takes 1 s, so against a 0.75 s threshold, dimmer
1.0 would always be "late". The routine (`MMcQueue::totalTime`) is kept, and
its inputs are given in SWIM's units: c = active servers, arrival rate λ, mean
service time df·S + (1 − df)·S_low. The value of S is the one input that the
port does not define. Three variants, each fixed before its result was seen:

| config | S (full content), S_low | |
|---|---|---|
| `pladapt_seams2017a` (**primary**) | 0.030 s, 0.001 s: the means of the servers' configured `serviceTime` / `lowFidelityServiceTime` | what SWIM's Model is meant to hold |
| `pladapt_seams2017a_maxrate` | 1/maxServiceRate = 0.0445 s, 0.001 s | SWIM's own "typical normal service time", the constant in the utility |
| `pladapt_seams2017a_stevensrt` | Stevens's inputs verbatim, result read as ms | for comparison only |

A bug to record: the first build took S from `Model::getServiceTime()`, which
is **0 in SWIM_SA** under OMNeT++ 5.4.1. SWIM's parameter parser returns 0
for `truncnormal(0.03s, 0.03s)` there, though the same logic standalone
returns 0.03; the root cause was not chased. The planner then believed
requests take no time, held 1 server and scored −24,520. The patch now reads
the mean from the server's parameter itself (the first argument of the
distribution) and logs the values each decision (`planningUtility=... serviceTime=0.03 ...`
in `swim.log`). No parameter was changed after seeing an outcome.

- **The objective is not the bottleneck; the performance model is.** With
  SEAMS 2017A the planner does what the function rewards: dimmer 1 and few
  servers. Whether that works depends on how well its M/M/c predicts SWIM.
- **Primary (0.030 s): too optimistic.** SWIM's real full-content service
  time is longer than 0.030 s. `truncnormal(0.03, 0.03)` has mean ≈ 0.039 s,
  and a server whose name has not served before starts with a cold cache that
  adds up to 50 ms per request (`MTBrownoutServer` caching effect). So the
  planner runs about 2 servers at dimmer 1 and is late in 59 of 90 periods.
- **0.0445 s variant: 4 late periods.** They fall just after it reshapes the
  pool under rising load: a server added at 2,580 s is active only at 2,760 s
  (SWIM boots in 3 periods, Stevens's relation models 2), and a removal at
  3,540 s precedes a late stretch. It acts in 15 of 91 decisions and is still
  1,629 below the best fixed configuration.
- **Why some SDs are 0.** The planner reads only arrivals, which come from the
  trace, so its decisions do not depend on the seed. A seed changes only
  response times. Where no period is near the threshold, or the same periods
  are far over it in every seed, the score is identical across seed-sets. The
  primary's SD (1,016) comes from periods near the threshold.

**No.** On both traces the best fixed configuration beats every adaptive
manager, and even re-choosing the best configuration every period adds at
most ~1,400. The reason is the utility, not the trace: below dimmer 1.0 every
configuration that is on time scores the same revenue whatever its server
count, and at dimmer 1.0 the server-cost credit (10 × (12 − servers) per
period, ~8,000 over a run) dominates. So "dimmer 1.0 with the fewest servers
that stay on time" wins, and both traces are scaled ("l70") so that 3-4
servers cover their peak (ClarkNet 15-71 req/s, WorldCup 7-70 req/s; one
server serves ~22.5 req/s at dimmer 1.0).

At high load SEAMS 2017A's late-period penalty, 1.5·(a − 269.5), also shrinks
as the arrival rate a grows, so late periods become cheaper.

### Thallium: not re-targeted

Thallium does not plan; it trims the relation PLA-SDP plans over. It does so
by Pareto dominance across three separate objectives (cost, fidelity, response
time), bounded by PRISM-games for best, expected and worst arrivals.
Re-targeting it to SEAMS 2017A is not a reward swap, for three reasons:

- SEAMS 2017A is one scalar whose terms interact: the cost credit is paid only
  at dimmer 1.0 and only when the period is not late. It does not split into
  three independent objectives. Pareto trimming on a single objective keeps
  only the best successor, which collapses the method.
- The SMG's response-time model is in its own units (SERVICE_RATE,
  DIMMER_ADJ, SECS_PER_STEP), so it would have to be re-expressed in SWIM's.
- The relation behind the shipped run is itself reconstructed by search.

Compute is not the obstacle: `thallium_search.py` re-implements the bounds in
under a second per setting. The obstacle is a design decision about what
Thallium should mean for a scalar objective, plus rewriting the SMG's reward
structures. That is more than an hour, and the result would be a new method
rather than Thallium. Skipped.
